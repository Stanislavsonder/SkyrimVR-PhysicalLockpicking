# CLAUDE.md

What you need to know to work on this repository. The player-facing description is in `README.md`.

## The project

**VR Physical Lockpicking** is an SKSE plugin for **Skyrim VR 1.4.15** (SKSEVR + VR Address Library). It replaces the flat lockpicking menu with lockpicking by hand. When the player activates a locked door or chest, a 3D lock appears in front of them. They put a lockpick into the keyhole with one hand and the tension wrench with the other, search for the sweet spot by controller vibration, and turn the lock.

Vanilla rules are kept:
- Lock level, skill and perks set the sweet spot and how long a pick lasts. Perks are found through their entry points, never by form ID, so mods' perks count the same way.
- Breaking picks costs a lockpick and gives XP. Opening a lock gives XP and counts in the "Locks Picked" statistic.
- The Skeleton Key works. Wax Key, crime, and opening the container afterwards work as in vanilla.

Lock Variations `_LID.ini` files are read so that each lock gets its own models and sounds.

The version is 1.0.1. `CHANGELOG.md` holds the release notes.

## Layout

| Path | What |
|---|---|
| `src/core` | Game-independent C++ (no CommonLib, no Windows): `LockSession` (the simulation: tools, sweet spot, strain, events, haptics), `Config` (all tunables + INI parsing), `LockProfile` (markup tool profiles, built-in tool alignments), `MeshFit` (placing lock / tool models from their bounds), `LockVariations` (`_LID.ini` reader), `Translations` (the game's translation files), `VecMath` (Vec3 / Mat3 / Quat / Pose, 1-euro filter). |
| `src/plugin` | The SKSE plugin. `main.cpp`: load, config loading, perk entry points, hand / wand nodes, Skeleton Key. `LockpickManager`: intercepts the menu, runs a session, pause, crime, unlock / break, markup tool flow. `Visuals`: the in-world lock and tool models. `VRInput`: SKSEVR controller hook, input blocking, OpenVR haptics thread. `FrameHook`: per-frame callback after the hand nodes move (HIGGS's spot). `AddressCheck`: gates engine calls on the installed address library. `DebugView`, `AssistRing`, `PickCounter`, `Markup`: things drawn on / around the lock. `TestLocks`, `DebugCheats`: MCM debug buttons (Papyrus natives). `LockMods`: Lock Variations in game. `Text`: the player's messages in the game's language. |
| `tests/test_core.cpp` | Unit tests for `src/core` (own tiny `TEST` / `CHECK` macros). They include a simulated shaky-handed player that must open every lock level. They also check the repo's consistency: versions, MCM keys vs defaults, the shipped INI vs `Config` defaults, every text in every language. |
| `package/` | What goes into the archive: `VRLockpicking.ini` (every setting, commented), `mcm/config.json` + `mcm/settings.ini` (MCM Helper menu and its defaults), `translations/` (menu and message texts per game language, UTF-8 here; `package.py` writes them as the UTF-16 files the game reads), `assets/` (the mod's own meshes / textures, generated by nifgen). |
| `tools/` | `package.py` (builds the zip, laid out as the game's `Data` folder with no installer: a player's MO2 crashed installing the 1.0.0 FOMOD, which had nothing to choose), `make_mcm.py` (writes `VRLockpicking.esp` (ESL-flagged) + the `VRLockpicking_MCM` script without the Creation Kit; called by `package.py`), `nifgen/` (generates `package/assets` meshes with nifly), `audit_address_ids.py` (lists the address IDs a built DLL uses). |
| `extern/CommonLibVR` | alandtse's CommonLibSSE-NG with VR support (git submodule). |
| `.github/workflows/build.yml` | CI: Linux core tests, Windows MSVC plugin build + tests + package, and a GitHub release on `v*` tags. |

## Building and testing

The core tests run anywhere and are the fast check:

```sh
cmake -S . -B build-tests -DVRLP_BUILD_PLUGIN=OFF
cmake --build build-tests
ctest --test-dir build-tests --output-on-failure   # or build-tests/vrlp_tests
```

**Plugin on Windows** (what CI does):

```sh
git submodule update --init --recursive
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=RelWithDebInfo -DCMAKE_TOOLCHAIN_FILE=%VCPKG_ROOT%/scripts/buildsystems/vcpkg.cmake -DVCPKG_TARGET_TRIPLET=x64-windows-static-md -DVRLP_BUILD_PLUGIN=ON
cmake --build build --target VRLockpicking vrlp_tests
python tools/package.py build/VRLockpicking.dll out/VRLockpicking.zip
```

**Plugin on Linux:** cross-compile with clang-cl (LLVM 20) and an `xwin` sysroot. Pass `-DCMAKE_TOOLCHAIN_FILE=extern/CommonLibVR/cmake/toolchain-linux-clangcl.cmake -DXWIN_SYSROOT=<xwin output> -DVRLP_BUILD_PLUGIN=ON`, then `ninja`. This is the way to check that plugin code compiles without Windows. CommonLib takes a long time the first time.

**Address IDs:** after a plugin build, run

```sh
python3 tools/audit_address_ids.py VRLockpicking.dll VRLockpicking.pdb <path to version-1-4-15-0.csv>
```

It needs the cross build's PDB and `llvm-pdbutil` / `llvm-objdump`. It fails if the DLL resolves an ID that `src/plugin/AddressCheck.h` doesn't list. With the CSV, it reports which IDs the public VR library lacks. The CSV is in CommonLibVR's `tests/REL/`. The known and accepted gaps are:
- 19110, used through a verified fixed offset;
- 51115;
- 97538, linked but never reached.

**Meshes:** see `tools/nifgen/README.md`. The generated files are committed, so you only regenerate them after changing `nifgen.cpp`. Check that the files you didn't mean to change come out byte-identical.

**MCM schema:** `package/mcm/config.json` can be validated against MCM Helper's `docs/config.schema.json`. That schema doesn't list a page's `cursorFillMode` (MCM Helper reads it, see its `PagesHandler.cpp`). It also rejects the stepper's `valueOptions.options`, which MCM Helper reads too. Those two reports are expected.

### Before every push

Each push to any branch runs the full CI build (about 10 minutes, produces the artifact `VRLockpicking-<run number>`). So:

1. Commit locally as you go. **Push only when the maintainer asks for a build.**
2. Before pushing, run the core tests, and for plugin changes also the cross build and the address audit. The consistency tests catch config / MCM / INI mismatches that compile fine.
3. Do not open pull requests unless asked.

## How things fit together

### Session flow

1. `LockpickManager` watches `LockpickingMenu` open events. With the mod on and the essential address IDs present, it closes the vanilla menu and starts its own session on the menu's target.
2. It does nothing in these cases, and the vanilla menu runs as normal:
   - the mod is off;
   - an essential ID is missing (the player is shown an update message);
   - there is no target;
   - the lock needs a key;
   - there are no lockpicks.
3. When the vanilla menu does run, `Visuals::NoteVanillaMenu()` is called (see below).
4. At session start:
   - gather the `LockParams`: lock level, skill, perk entry points, the Skeleton Key, Locksmith's starting arc;
   - build the lock frame in front of the headset, in **room space** (tracking space), so locomotion moves the room and not the lock relative to the player;
   - create the visuals and overlays;
   - block input (`VRInput::SetBlocking`);
   - pause the world (full pause by default);
   - mute the game's rumble.
5. Each frame, the controller callback schedules `Update` on the main thread. It feeds hand poses and buttons to `LockSession` and reacts to its events: tool in / out, pick broken, unlocked. `FrameHook` re-places the models right after the game moves the hand nodes, so they don't trail by a frame.
6. On unlock, the plugin:
   - unlocks the reference and records the change;
   - gives the XP and the statistic;
   - handles Wax Key (key reward chance) and crime;
   - optionally opens the container.

   On give-up (B / Y), walking away or a pausing menu, `End()` tears everything down.

### Settings pipeline

The places that state a setting must all agree; the tests enforce it.

- `src/core/Config.h`: the field and its default; `Config.cpp` parses it (`section.key`, case-insensitive).
- `package/VRLockpicking.ini`: every setting, with a comment, with the default value (`ShippedIniMatchesDefaults`).
- For settings offered in the MCM:
  - a control in `package/mcm/config.json` with `"id": "key:Section"`;
  - the same key with its default in `package/mcm/settings.ini` (`McmDefaultsMatchConfig`).

  Taking a setting out of the menu means removing it from **both** MCM files.

Texts: every label, help text, page name and stepper option in `config.json` is a `$VRLP_...` key. So is every message the plugin shows the player (`Text::Show` / `Text::Format`, which read the same files in the game's `sLanguage`, falling back to English). Each key needs a line in **every** `package/translations/VRLockpicking_<LANGUAGE>.txt` (ENGLISH, FRENCH, GERMAN, ITALIAN, SPANISH, POLISH, RUSSIAN, JAPANESE, CHINESE), with the same `{}` placeholders; a language without its file would show raw keys (`TranslationsCoverEveryText`). Messages only the debug view shows stay in English.

Load order: `SKSE/Plugins/VRLockpicking.ini`, then `MCM/Settings/VRLockpicking.ini` (MCM Helper writes only the changed keys). Of the MCM file, only keys the menu still offers are applied. `McmSettingKeys` reads them out of `config.json`, so stale values from removed options never apply unseen. Settings are re-read when the journal closes and take effect at the next session.

MCM layout: each page uses `"cursorFillMode": "topToBottom"`. The right column starts at a control with `"position": 1`. A position counts left to right, row by row (row r, column c = 2r + c), and `{"type": "empty"}` makes a spacer row.

MCM buttons are `text` controls with a `CallGlobalFunction` action on `VRLockpicking_MCM`. To add one:
- add the function name to `NATIVES` in `tools/make_mcm.py`;
- implement and register the native in `DebugCheats.cpp` or `TestLocks.cpp`;
- gate it in `AddressCheck` if it needs engine IDs.

### Address library gating

The public VR Address Library can be older than CommonLib. Resolving a missing ID shows a message box that is invisible in the headset, so the game looks frozen. `AddressCheck` reads the installed CSV, and every engine feature checks its IDs (`AddressCheck::Has(Ids::...)`) before calling. Optional features turn themselves off and log it; essential ones fall back to the vanilla menu. **Any new CommonLib call that resolves an ID must be added to `AddressCheck.h`** (the audit enforces it).

### Models (hard-won facts)

- **The game's model cache shares one master per .nif; `Clone()` copies its current state.**
  - The vanilla lockpicking menu animates the shared `LockPickShiv01.nif` and the lock models: the cylinder is turned, the shiv slid in. It leaves them in that pose. `Visuals` puts the vanilla lock into a hardcoded rest pose (`RestPoses()`, taken from logs). For other lock models it snapshots the pose (`CollectPose` / `ApplyPose`) before the vanilla menu has run (`g_vanillaMenuRan`).
  - **Inventory models (the lockpick, the Skeleton Key) share their rigid body with the world object.** Strip collision from every clone (`StripCollision`) before its first update. Otherwise the clone's physics drags the shared body and the pick vanishes.
- Tools: the lockpick model's shape is fixed in code. The Skeleton Key uses its own model, flipped, with a built-in alignment. The tension wrench is the lock model's `Shiv` part (the "screwdriver"; the official name is tension wrench). Built-in alignments are in `DefaultToolProfiles()` (`LockProfile.cpp`), lined up in game with the markup tool. A player's own profile in `VRLockpicking_Locks.ini` wins.
- `MeshFit` places models from their bounds: keyhole at the origin, +Y into the lock, +Z up; tools with the tip at the origin and the shaft along -Y.
- Coordinates follow NetImmerse: right-handed, Z up; `Mat3` is row-major and its columns are the local axes. Lock frame: x right, y into the lock, z up.

### Perks and items

All perks are read through entry points as the vanilla menu asks for them (`main.cpp`):
- `kModLockpickSweetSpot`;
- `kSetLockpickStartingArc`: Locksmith, about 45°. The sweet spot is moved to within that arc of where the pick first goes in;
- `kMakeLockpicksUnbreakable`;
- `kModLockpickingKeyRewardChance`: Wax Key;
- `kModLockpickingCrimeChance`.

The Skeleton Key is `DefaultObjectID::kSkeletonKey`. While carried, picks are unbreakable and the key is the pick.

## Conventions

- C++23 for the plugin and C++20 in `src/core`. Tabs. Braces on their own line for functions, types and namespaces. CommonLib style: `a_` prefix for parameters, `_` for members, `k` for constants. Everything is in `namespace vrlp`.
- Comments are plain sentences that say *why* and what a thing means in game terms, at the density of the surrounding code. The header comments describe each class's behaviour for a player-level reader.
- Windows headers can leak macros. `PCH.h` handles this; `#undef GetObject` where needed.
- Logging goes through `logger::info/warn` to `Documents/My Games/Skyrim VR/SKSE/VRLockpicking.log`. Verbose output is behind `bDebugLogging`. When diagnosing something in game, add a log line and ask for the log rather than guessing.
- Docs (README, INI comments, MCM help texts, CHANGELOG) are plain, short English for players. Keep them in sync with behaviour in the same commit: a removed option leaves no mention anywhere.
- **Version:** `project(VRLockpicking VERSION x.y.z)` in `CMakeLists.txt` is the source. `src/plugin/Version.h`, `src/plugin/version.rc`, and `vcpkg.json` must match (`VersionsMatch`). Add a `## x.y.z` section to `CHANGELOG.md`.
- **Release:** push a `v<version>` tag. CI attaches the zip to a GitHub release with that version's CHANGELOG section as the notes.

## Testing in game

There is no game in CI. Behaviour is verified by the maintainer in Skyrim VR. The Debug page of the MCM has tools for this:
- debug log, debug view and keyhole target;
- the assist ring and the model markup tool;
- crime detection;
- spawning test chests and doors (one per lock model, levels shared out);
- buttons for lockpicks, the Skeleton Key, perks and the skill level.

When asking for a test, say what to do and what to look for in the log.
